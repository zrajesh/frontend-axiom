# Audit: Frontend Axiom (self-audit)
Date: 2026-09-18 · Reviewed: entire plugin — `.claude-plugin/plugin.json`, `.mcp.json`, `knowledge/*.md` (10 files), `skills/*/SKILL.md` (5 files), `agents/*.md` (2 files), `eslint-plugin-frontend-axiom/**`, `README.md`

## Verdict

Not ready to govern production work at millions-DAU scale. What exists is a well-written, internally coherent *code-style and component-hygiene* guide — SOLID, a destructuring convention, five-state data handling, CWV targets, a reasonable CSP/storage/HTTP-caching primer. That is real value and it's mostly accurate. But it stops at the boundary of "code that looks clean in a PR." There is zero mention of testing (unit, integration, E2E, visual regression), zero mention of CI/CD or release mechanics (canary, feature flags, rollback), and zero mention of production observability (error tracking, RUM, alerting) anywhere in `knowledge/`, `skills/`, or `agents/` — confirmed by exhaustive grep, not sampling. An app built by `frontend-architect` and blessed by `code-auditor` could pass every check in this plugin and still ship with no tests, no way to detect it's broken in production, and no way to safely roll it back if it is. At millions-DAU scale that is not a gap in polish, it's a missing half of the discipline the plugin claims to provide ("architecture that serves millions of users daily"). The single biggest thing holding this back is the absence of a testing standard — everything downstream (CI gates, safe rollout, confidence to audit-and-merge) depends on it existing first. A secondary, structural problem: the `new-feature` skill never actually invokes the `frontend-architect` subagent it's advertised to use (see Critical #4), and the `audit` skill's isolation mechanism is explicitly self-flagged as unverified — so even the workflow this plugin does define may not run the way its own README claims.

## Critical

### 1. No testing standard exists anywhere in the plugin
Grep across all of `knowledge/`, `skills/`, `agents/` for `test|jest|vitest|playwright|cypress|storybook` returns only incidental noise (`css.md:33` "test real breakpoints", `accessibility.md:25` a testing *section* about a11y only, `learn-guide/SKILL.md:20` naming "testing strategy" as an example of a domain *not yet covered*). There is no `knowledge/testing.md`. `new-feature/SKILL.md`'s Step 3 "build" (lines 26-31) and Step 4 self-check (lines 33-35) never mention writing a test. `frontend-architect.md`'s "before you say you're done" checklist (lines 29-31) checks dot-chaining, SOLID, data states, and secrets — not test coverage. `audit/SKILL.md`'s output checklist (lines 44-53) has no "Tests" row, and `code-auditor.md`'s "what to check" list (lines 19-25) never asks whether the feature has any automated test.

**Why it matters at millions-DAU scale**: this tooling's entire pitch is that an AI agent can be trusted to build and independently gate production frontend code. Without a testing requirement, "the audit passed" tells you the code is stylistically compliant, not that it works, not that it keeps working after the next change, and not that a regression will be caught before 10M users hit it. This is the single highest-leverage gap in the whole plugin.

**Fix**: add `knowledge/testing.md` covering: unit/component testing with React Testing Library + Vitest/Jest (test behavior, not implementation — no snapshot-testing markup as a substitute for assertions); a coverage floor tied to risk (e.g., 100% on payment/auth/data-mutation logic, pragmatic elsewhere — not a blanket arbitrary %, which is itself a common anti-pattern); mandatory MSW-based mocking for RTK Query endpoints in component tests instead of hitting real network; E2E coverage (Playwright) for the critical user journeys (checkout, signup, auth) as a release gate, not "nice to have"; visual regression (Chromatic/Percy) wired into `pixel-check`'s workflow so a design-match, once achieved, doesn't silently drift; and CI must fail the build on test failure. Then wire it into `new-feature` (write tests as part of Step 3, not after), `frontend-architect.md`'s pre-done checklist, and `audit/SKILL.md`'s checklist table (a "Tests" row).

### 2. No production observability / error-tracking / RUM standard
Grep for `sentry|observability|monitoring|rum|error track|datadog|logrocket` across `knowledge/`, `skills/`, `agents/` returns nothing relevant. `performance.md`'s only verification mechanism for Core Web Vitals is "`/pixel-check` and `/audit` should check these via the Chrome DevTools MCP's performance trace tooling" (`performance.md:13`) — a one-off **lab** measurement taken during a review session. Google's own CWV "Good" thresholds (the ones this file cites) are defined against **field data** (CrUX / real-user monitoring), not lab traces — a single Chrome DevTools trace on a developer's machine tells you almost nothing about what millions of real users on real networks and real devices are experiencing. There is also no guidance on structured logging, no error-boundary-to-error-tracker wiring (`react-nextjs.md:41` mentions `error.tsx` but never what happens to the error it catches), and no mention of `web-vitals` JS library reporting to real analytics.

There's also an unaddressed tension the plugin creates with itself: `security.md:43` correctly says "don't serve production source maps publicly," but nothing anywhere explains the standard resolution (upload hidden source maps to the error tracker at build time for symbolicated stack traces) — so following `security.md` as written leaves production errors permanently unreadable (minified, unsymbolicated) unless a team independently figures out the missing piece.

**Why it matters at millions-DAU scale**: without RUM and error tracking, the organization is blind to whether the product is actually broken for users right now, and blind to whether it's actually meeting the performance targets this plugin itself defines. "Serves millions of users daily" without a way to know if it's currently failing for a meaningful fraction of them is not production-grade.

**Fix**: add `knowledge/observability.md` covering: client error tracking (Sentry or equivalent) wired to error boundaries and unhandled-rejection handlers, with PII scrubbing rules for breadcrumbs/payloads; the source-map-upload-not-serve pattern that resolves the `security.md:43` tension; RUM via the `web-vitals` library reporting real LCP/INP/CLS to analytics, with alerting thresholds tied to the targets already defined in `performance.md:3-11`; structured logging conventions for what a frontend is even allowed to log (no PII/tokens); and dashboards/alerts as a release-readiness gate, not an afterthought.

### 3. No release/deployment/rollback/feature-flag standard — the workflow stops at "merged"
Grep for `feature flag|launchdarkly|canary|rollback|blue-green|ci/cd|continuous` across the plugin returns nothing about deployment (the one "rollback" hit, `state-data.md:20`, is about optimistic-update UI rollback, unrelated). The five skills cover: detect/scaffold stack (`init-project`), interview+plan+build (`new-feature`), visual diff (`pixel-check`), independent review (`audit`), and ingest a doc (`learn-guide`). None of them, and no `knowledge/*.md` file, addresses what happens between "code is merged" and "code is safely serving traffic to millions of users": no feature flags / kill switches, no canary or staged rollout, no environment promotion (dev → staging → prod), no rollback procedure, no mention of preview deployments for review.

**Why it matters at millions-DAU scale**: at that scale, "ship a bad build straight to 100% of users with no kill switch" is the textbook cause of major incidents. A tool that governs "how code gets designed, written, and reviewed" (per its own framing) but has nothing to say about how it gets *released* is missing the step where most real-world outages actually happen.

**Fix**: add `knowledge/release-operations.md` (or fold into a new `knowledge/ci-cd.md`) covering: feature-flag-gated rollout for any change with meaningful blast radius, with an explicit kill switch; staged/canary rollout percentages and the metric-based promote/rollback criteria (tied to the observability standard above); required CI gates before merge (lint at `error` not `warn` — see Major #2 below —, typecheck, tests, bundle-budget check, a11y scan); and a documented rollback procedure. Add a corresponding step to `audit/SKILL.md`'s checklist ("is this change flag-gated / does it have a rollback path") for anything above a trivial blast radius.

### 4. `new-feature` never actually invokes the `frontend-architect` agent it's advertised to use
`README.md:57` states: "`/frontend-axiom:new-feature` — ... asks first, plans, then builds using the `frontend-architect` agent." But `skills/new-feature/SKILL.md` contains **no reference to `frontend-architect` anywhere** (verified by grep: the only file matches for "frontend-architect" in the whole repo are `agents/frontend-architect.md` itself and `README.md`). Step 3 "build" (`new-feature/SKILL.md:26-31`) just restates the rules inline — it never delegates via the Task/Agent mechanism, and `new-feature/SKILL.md`'s frontmatter (`allowed-tools: Read, Glob, Grep, Bash, Write, Edit, AskUserQuestion`) doesn't even include a delegation tool. Compare this to `audit/SKILL.md:4-6`, which explicitly declares `context: fork` + `agent: code-auditor` to force delegation to the auditor subagent.

So of the plugin's two subagents, only one (`code-auditor`) has an explicit, mechanical wiring to get invoked. `frontend-architect.md`'s description ("Use proactively for any code-writing task in a Frontend Axiom project," line 3) is the only thing that could cause it to fire, and that depends entirely on Claude Code's own implicit subagent-routing heuristics choosing to invoke it during a `/new-feature` run — which is not guaranteed, not documented as reliable by Claude Code itself, and is exactly the kind of thing the README already flags as unverified for the *audit* side (`README.md:89`) but doesn't even acknowledge as a risk on the *build* side. In practice this likely means `new-feature` just runs inline in the main conversation, with no isolation and no guarantee the dedicated architect persona/prompt is ever actually loaded — undermining the two-agent "build vs. independently review" architecture the README presents as the product's design.

**Why it matters at millions-DAU scale**: this isn't cosmetic — it means the actual behavior of the most-used skill in the plugin (`new-feature`) rests on an implicit, unverified routing assumption rather than an explicit contract, which is precisely the failure mode this audit was asked to hunt for (finding #7, "will these prompts actually produce the intended behavior").

**Fix**: either (a) make `new-feature/SKILL.md` explicitly delegate to `frontend-architect` the same way `audit/SKILL.md` delegates to `code-auditor` (add the same `agent:`/delegation wiring, or an explicit "invoke the frontend-architect agent via the Agent/Task tool" instruction), or (b) if inline execution in the main conversation is actually intended, delete the "builds using the `frontend-architect` agent" claim from `README.md:57` and merge `frontend-architect.md`'s content directly into `new-feature/SKILL.md` so there's one source of truth. Then verify the chosen behavior end-to-end the same way the README already did for `plugin details` (`README.md:47-52`), rather than leaving it asserted-but-unverified.

### 5. The mandatory destructuring rule is written to be actively harmful to TypeScript discriminated unions and to React referential stability — exactly where it's mandated most
The rule (`principles.md:17-33`) is stated as a hard, non-negotiable rule with narrow exceptions, and is meant to apply "at any nesting depth" to "function params, hook returns, API responses, and context values" (`principles.md:26`). Two concrete ways this backfires in the TypeScript + React stack this plugin defaults to (`react-nextjs.md`, project default is TS per `README.md`/`init-project`):

- **Discriminated union narrowing breaks under destructuring.** A very common frontend pattern — reducers, RTK Query response unions, `action.type`-driven branching — relies on TypeScript narrowing a variable by checking a discriminant field (`action.type === 'x'`) and then reading the now-narrowed variable's other fields. Once you destructure the discriminant and payload apart (`const { type, payload } = action`), TypeScript can no longer correlate them — narrowing on `type` does not narrow `payload`'s type, and if the payload field differs per union member, upfront destructuring of all variants together often won't even compile. The rule as written gives an agent no escape hatch for this — it isn't in the three narrow exceptions listed (`principles.md:29-31`), and the ESLint heuristic (see #6 below) can't tell the difference between an ordinary object and a discriminated union, so it will flag `action.type` + `action.payload` accessed in different `case` branches of the same `switch` (same function scope) as a violation even though destructuring them together is the wrong fix. This is a rule that, applied literally in the exact language the plugin defaults to, produces measurably less type-safe code.

- **Default values in destructuring create new references every render.** The convention's own canonical example (`principles.md:22-23`, repeated in `README.md:67-68`) is `const { skills = [] } = user;`. Every time `user.skills` is `undefined`, this allocates a **new** array literal on that render. If `skills` is then passed to a memoized child, used as a `useMemo`/`useCallback`/`useEffect` dependency, or passed to `React.memo`-wrapped component, this silently defeats the memoization/dependency-tracking guidance the plugin itself gives in `react-nextjs.md:35-36` ("`useMemo`/`useCallback` are for... referential stability required by a memoized child") — the destructuring rule and the memoization guidance actively contradict each other for any array/object-valued default, and nothing in either file calls this out.

**Why it matters at millions-DAU scale**: a house rule enforced by prompt *and* CI lint, with no documented workaround, that quietly (a) degrades type safety in the mandated language and (b) reintroduces the exact referential-instability bugs the performance guidance warns against, will get baked into thousands of call sites before anyone notices — and "the linter told me to" is a bad place to discover a production bug.

**Fix**: add an explicit fourth exception to `principles.md` §3: discriminated unions/tagged variants read after a narrowing check on the same (non-destructured) variable are exempt — narrow first, destructure per-branch after, or don't destructure the payload field at all. Add a rule to only default-destructure primitives inline; object/array defaults for anything that can reach a dependency array or memoized prop should be hoisted to a module-level constant (`const EMPTY_SKILLS: string[] = []`) or handled with `??`/a stable empty-array helper, not a fresh literal per destructure. Update the ESLint rule's `ignore` guidance and README to document this pattern explicitly, since the linter cannot detect it on its own (see #6).

## Major

### 1. Missing/thin coverage of auth architecture, privacy/consent, i18n, and component-library governance
`security.md` and `storage.md` cover *where* to put a token but nothing about the surrounding auth architecture: OAuth/OIDC/SSO flows, refresh-token rotation, silent refresh, multi-tab session sync, or "logged out everywhere" UX. Grep for `oauth|oidc|sso|refresh token` (beyond the storage-location mentions) returns nothing. There is no `knowledge/auth.md`. Similarly, grep for `gdpr|ccpa|consent|privacy|cookie banner` returns **zero hits** anywhere in `knowledge/`, `skills/`, or `agents/` — for a tool explicitly scoped to products serving millions of users (almost certainly spanning the EU/UK/California), the complete absence of consent-management, cookie-banner, or PII-minimization-in-analytics guidance is a real gap with legal exposure, not just a nice-to-have. `i18n|locale|hreflang|translat` likewise returns nothing beyond `locale` appearing once as an example *value* in `storage.md:8` — there's no internationalization guidance and `seo-ai-seo.md` never mentions `hreflang` or locale-aware sitemaps, which is a real SEO gap for any global product. Design-system/component-library governance (Storybook, component API versioning) is only mentioned once, in `learn-guide/SKILL.md:20`, as an example of a domain *not yet covered*.

**Fix**: add `knowledge/auth.md` (session/token lifecycle, refresh strategy, route protection/middleware, logout-everywhere), `knowledge/privacy-compliance.md` (consent management, cookie categorization, analytics PII rules, data-subject-request handling from the frontend's perspective), and `knowledge/i18n.md` (message extraction/ICU format, locale routing, RTL, locale-aware formatting, `hreflang` + localized sitemaps — cross-reference from `seo-ai-seo.md`). Component-library/Storybook governance can be lower priority but should exist before this plugin is used by more than a single-team codebase.

### 2. Performance and lint guidance is frequently hand-wavy where an engineer needs a decision rule, not a value judgment
- `performance.md:26`: "flag anything that meaningfully grows the shipped JS for a marginal feature" — gives an agent no actual number to check against. Compare to how precisely CWV targets are specified (`performance.md:3-11`) — bundle size deserves the same treatment: a concrete per-route JS budget (e.g. gzip/brotli KB ceiling) enforced by a CI tool (bundlesize, `next build` output diffing, or Lighthouse CI budgets), not a prose "flag anything that meaningfully grows."
- `init-project/SKILL.md:51`: "Leave it at `warn` initially... that's expected, and is signal for `/frontend-axiom:audit` to triage" — no skill or agent ever revisits this. There's no defined trigger for promoting `frontend-axiom/no-repeated-property-access` (or `prefer-destructuring`) from `warn` to `error` in CI, so on a real codebase this plausibly stays a permanently-ignored warning forever — a lint rule at `warn` with no enforcement gate is close to decorative at scale, and this plugin doesn't even try to close that loop.
- `accessibility.md:28`: "a keyboard-only pass and a screen-reader spot-check on any new significant flow" — "significant" is undefined; nothing tells an agent (or a human reading an audit) what qualifies.

**Fix**: replace each of these with a concrete number/gate: a per-route JS budget in `performance.md`, an explicit "promote `no-repeated-property-access` to `error` once the codebase warning count is 0, and gate CI on it thereafter" instruction in `init-project` (or `audit`), and a concrete definition of "significant flow" (e.g., any flow gated behind a route with a `generateMetadata`/indexable page, or any flow involved in a core conversion funnel).

### 3. The ESLint heuristic has real, exploitable false-negative modes beyond what its own README documents
The README (`eslint-plugin-frontend-axiom/README.md:32-35`) documents one false-positive class (nested design-token objects like `theme.colors`/`theme.spacing`) but the rule has several unexamined **false-negative** modes that matter more, because they mean the "CI-enforced version" of the house rule silently doesn't catch its own textbook target cases:
- **Multi-hop chains are barely checked.** The rule only records a property when `node.object.type === "Identifier"` (`no-repeated-property-access.js:119`). For `data.user.email` — a 3-level chain, and literally the exact shape principles.md is arguing against (`data.user.email`-style access, c.f. `principles.md:19`) — only the inner `data.user` hop qualifies (base `data`, prop `user`); the outer `.email` hop's object is a `MemberExpression`, not an `Identifier`, so it's invisible to the rule. A single occurrence of `data.user.email` in a scope produces **zero** warnings (only 1 distinct property recorded, below the threshold of 2). Deep chains are the rule's blind spot, not its strength.
- **`this.props.x` / `this.state.x` are entirely invisible.** Same root cause: `this` is a `ThisExpression`, not an `Identifier`, so class-component-style access is never evaluated by this rule at all.
- **Violations split across sibling closures in the same function are never caught**, because the rule resets its per-base budget at every `Function*`/`ArrowFunctionExpression` boundary (`no-repeated-property-access.js:107-115`, `pushScope`/`popScopeAndReport` on scope entry/exit) rather than tracking where the *base identifier* was actually declared. E.g.:
  ```js
  function ProductRow({ product }) {
    const handleClick = () => trackClick(product.id);
    const handleHover = () => trackHover(product.name);
  }
  ```
  `product.id` and `product.name` are two distinct properties of the same closed-over variable, which is exactly what the rule exists to catch — but because each arrow function gets its own fresh scope map, neither ever reaches the threshold of 2. This is a common React shape (several small handlers each touching one field of the same prop), and it slips through entirely.

**Why it matters**: the plugin's whole pitch for the linter is "not just by convention" (`README.md:31`) — i.e., it's supposed to be the backstop when the prompt-level instruction fails. These aren't exotic edge cases; multi-hop chains and per-handler closures are extremely common shapes, so the backstop has large, easily-hit holes for the exact pattern it's meant to enforce.

**Fix**: document these three cases explicitly in the plugin's own README (not just the theme.colors case), and consider a real fix for at least the multi-hop case — walk the full `MemberExpression` chain from a given root `Identifier` and count each `.property` hop along the chain, not just the innermost one. The closure-scope case is harder (needs actual variable-declaration tracking via ESLint's scope manager, not ad hoc `Map` stacks keyed by AST node type) — worth a note that this is a known limitation rather than silence.

### 4. `init-project` reads a narrower knowledge slice than the agents it's supposed to set the foundation for
`init-project/SKILL.md:59` (Step 4) instructs reading only `knowledge/principles.md`, `knowledge/react-nextjs.md`, `knowledge/css.md`, and `knowledge/state-data.md` before scaffolding — it omits `security.md`, `performance.md`, `accessibility.md`, `storage.md`, `seo-ai-seo.md`, and `caching.md`, and (unlike `frontend-architect.md:12` and `code-auditor.md:15`) has no "and any other relevant file" catch-all. Concretely, this means the skill whose entire job is to lay the foundation of a new project has no instruction to set up baseline security headers (CSP, HSTS, etc. from `security.md`), no a11y linting (`eslint-plugin-jsx-a11y`), and no cache-control defaults — all of which are far cheaper to establish at scaffold time than to retrofit later.

**Fix**: extend the Step 4 reading list to match the other two agents' pattern (full `knowledge/` sweep + catch-all), and add explicit scaffold-time actions: baseline security headers in `next.config`, `eslint-plugin-jsx-a11y` wired alongside the frontend-axiom ESLint plugin, and a starter `robots.txt`/`sitemap` stub.

### 5. `audit`'s default scope depends on a git-tag convention (`audit-baseline`) that no skill ever creates or advances
`audit/SKILL.md:15`: "default to the diff against the last commit tagged `audit-baseline`... or ask the user." No skill (`init-project`, `new-feature`, or `audit` itself) ever creates this tag, and nothing moves it forward after a successful audit. In practice this default branch of the logic will almost always fail to find the tag on a real project and fall through to asking the user — which mostly defeats the point of having a documented default — and even if a team manually adopts the convention, without something advancing the tag after each audit, the "default" diff scope grows to include everything since the *first* audit, not just what's new since the *last* one.

**Fix**: either have `audit/SKILL.md` itself move the `audit-baseline` tag forward on a clean/passing run (with user confirmation), or drop the tag-based default entirely in favor of something that doesn't require unstated external bookkeeping (e.g., default to the diff against the default branch, or against the last commit, and always state the scope explicitly in the report header).

### 6. `frontend-architect` has no tool restriction at all, unlike `code-auditor`
`code-auditor.md:4` explicitly whitelists `tools: Read, Grep, Glob, Bash, Write` (deliberately no `Edit`, since an auditor shouldn't modify code under review — good design). `frontend-architect.md`'s frontmatter (lines 1-6: `name`, `description`, `model: inherit`, `color`) has **no `tools:` field**, meaning — assuming Claude Code's default-inherit-everything behavior for an agent with no explicit tool list — the build agent has unrestricted tool access, broader than the reviewer that's supposed to be the check on it. There's no documented rationale for why the builder needs strictly more latitude than the auditor.

**Fix**: give `frontend-architect.md` an explicit `tools:` allowlist mirroring its actual needs (Read/Write/Edit/Glob/Grep/Bash/AskUserQuestion, plus the Figma/Chrome DevTools MCP tools if it's expected to self-check against a design mid-build) rather than relying on implicit full inheritance.

### 7. No guidance on list virtualization, cursor pagination, or real-time (WebSocket/SSE) patterns despite both being explicitly surfaced as questions to ask
`new-feature/SKILL.md:15` explicitly tells the agent to ask the user about "real-time updates" and pagination as edge cases, and `code-auditor.md:25` checks for "unbounded lists with no pagination/virtualization" — but no `knowledge/*.md` file actually teaches *how* to implement either. There's no virtualization threshold (e.g., "lists likely to exceed ~100 rendered rows should use `react-window`/`react-virtual`"), no cursor-vs-offset pagination decision criteria, and no WebSocket/SSE reconnection/backpressure guidance anywhere — `state-data.md` is entirely built around RTK Query's request/response model. The interview step asks the right question; nothing in the knowledge base tells the agent what to do with the answer.

**Fix**: add a short section to `performance.md` or `state-data.md` on virtualization thresholds and cursor-based pagination, and either a `knowledge/realtime.md` or a section in `state-data.md` covering RTK Query's `streamingUpdates` / a WebSocket-store pattern, reconnect/backoff, and how it interacts with the 5-state model (a 6th "connection lost, showing last-known data" state is arguably needed here and isn't in the current 5-state list at `principles.md:44-51`).

Those two never get a checklist row, so a reader comparing audits across features has no consistent pass/fail record for caching or data-layer normalization even though the process claims to review them. Add "Caching" and "State/Data layer" rows.

Not wrong to track them, but the table header conflates two categories; consider splitting into "Core Web Vitals" (LCP/INP/CLS) and "Other key metrics" (FCP/TTFB) so an agent doesn't misreport which metrics are actually CWV in an audit doc.
- `security.md` covers CSP/XSS/CSRF/headers well but never mentions Trusted Types (a real, increasingly-recommended DOM-XSS mitigation layered on top of CSP) — worth a line given the file otherwise tracks fairly current CSP practice (`strict-dynamic`, nonces).
- `.mcp.json:4` registers the Figma MCP at `https://mcp.figma.com/mcp`. Verify this endpoint against current Figma documentation before relying on it — Figma's Dev Mode MCP server has historically been exposed locally via the desktop app rather than as a fixed hosted URL, and remote-hosting details may have changed since this reviewer's knowledge cutoff. If wrong, `pixel-check` silently can't reach Figma at all.
- `eslint-plugin-frontend-axiom/package.json:12` declares `"eslint": ">=8"` as a peer dependency, but the test suite (`tests/no-repeated-property-access.test.js:6-8`) configures `RuleTester` with `languageOptions` — the flat-config-style option shape most reliably supported starting with ESLint 9. The README's own "Status" section (`eslint-plugin-frontend-axiom/README.md:85`) only claims verification "through the `eslint` CLI in a real ESLint 9 flat-config project" — i.e., the `>=8` peer range is asserted but not actually verified against ESLint 8. Either narrow the peer range or verify it.
- No skill ever revisits/promotes the ESLint rule severity from `warn`→`error` (also noted in Major #2) — listing it here too since it's as much a "loose end" as a hand-wavy rule.
- `README.md:52` says the expected component inventory is "5 skills, 2 agents, 2 MCP servers" as a way to self-verify wiring — good practice; consider a similar one-line "expected knowledge file count" sanity check now that `learn-guide` can silently add new files, so drift is easy to notice.
- Monorepo/multi-team conventions (CODEOWNERS, workspace boundaries) are entirely unaddressed. Lower priority than the Major/Critical gaps, but worth a placeholder note given the stated scale implies multiple contributing teams.
